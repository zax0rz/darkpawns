# Port Fidelity Audit: Module 45 (`redit.c`)

This audit examines the port fidelity between the legacy C source file `src/redit.c` and its Go counterparts in `pkg/`.

## 1. Architectural Mapping & Discrepancies

### C Source File
- **File**: `src/redit.c` (1,079 lines)
- **Functions & Features**:
  - **OasisOLC (On-line Creation) Room Editor**: Implements interactive Telnet menu structures (`redit_disp_menu`, `redit_parse`) allowing developers or builders with appropriate IMMORT/BUILDER flags to create new rooms (`redit_setup_new`), load existing rooms (`redit_setup_existing`), modify fields, and save changes to disk (`redit_save_to_disk`) or memory (`redit_save_internally`).
  - **Room Properties Editor**: Live modification of names, descriptions, room flags (safe, dark, peaceful, death), sector types (inside, forest, mountain, swim), extra keywords, exits (keyword, locks, keys, targets), and attached room scripts.
  - **Memory Refactoring**: Updates other exits and zone reset lists dynamically across the live server to preserve pointers and prevent creep whenever a new room is inserted (`redit_save_internally` shifting index allocations).

### Go Port Files
- **OMITTED (OLC System)**:
  - There is **no in-game interactive Go room editor**. The Telnet menu parsing loop is completely bypassed in the Go server.
- **Boot Parsing System**:
  - [pkg/parser/wld.go](file:///Users/zach/.openclaw/workspace/darkpawns_repo/pkg/parser/): Parses legacy Diku/CircleMUD-format `.wld` text area files at boot time, correctly reading all fields (names, description strings, exit settings, keys, flags, sectors, extra descriptions, and attached Lua script triggers).
- **Dynamic State Persistence**:
  - [pkg/game/save.go](file:///Users/zach/.openclaw/workspace/darkpawns_repo/pkg/game/save.go): Persists runtime room modifications (such as doors opened/closed/locked by players, and items dropped on the ground) across server restarts using a centralized `./data/world_state.json` file.

## 2. High-Fidelity Validation of Parsed & Saved Fields

The boot parsers in `pkg/parser/` achieve full structural compatibility with the legacy `.wld` disk formatting generated by C's `redit_save_to_disk` (`src/redit.c#L283-L394`):

1. **Exits & Doors Parsing**:
   - **C Save Routine**: Writes exit sections prefixed with `D[direction]`, followed by description text, keywords, and space-separated integers `[door_flags] [key_vnum] [target_room_vnum]`.
   - **Go Parser**: Correctly parses this structure, reading keywords, keys, target vnums, and translating door flags (`0` = no door, `1` = closeable door, `2` = pickproof door) into clean typed Go fields.
2. **Room Extra Descriptions**:
   - **C Save Routine**: Formats custom room keywords (e.g. looking at a sign, painting, or tree) using the `E` block prefix.
   - **Go Parser**: Correctly parses arbitrary arrays of extra descriptions, populating `RoomInstance` maps to enable high-fidelity `look [keyword]` commands.
3. **Attached Scripts (R line)**:
   - **C Save Routine**: Writes `R [script_name] [script_flags]` to associate room triggers.
   - **Go Parser**: Correctly reads the script properties, instantiating the Lua runtime scripting engine for matching rooms on startup.

## 3. Go's Architectural Improvements Over C

By deprecating the legacy in-game interactive Telnet editor in favor of offline area declarations and dynamic JSON state tracking, Go achieves major structural advancements:

### 1. Separation of Static Content from Dynamic State
In legacy C, any runtime change (like a player locking a door) had to either be written back to the primary `.wld` area file (risking corruption of build files) or was lost on restart. 
Go separates these concerns cleanly:
- **Static files** (`.wld` files under `lib/world/`) serve as read-only configurations, enabling clean Git tracking and version control.
- **Dynamic state changes** (door locks, items left on the ground, custom active variables) are cleanly serialized to `./data/world_state.json` on shutdown, ensuring high-fidelity persistency without altering core area assets.

### 2. Elimination of Unsafe Memory Pointer Swapping
In legacy C, dynamically inserting a new room in the middle of a zone required allocating a new global world array, copying all existing rooms, freeing the old pointers, and iterating through all exits, characters, objects, and zone command lists to increment and correct array offsets (`temp_ch->in_room = i + 1`, `ZCMD.arg3++`, etc.).
Go handles all room lookups via a safe, lock-guarded pointer map inside the `World` system (`w.rooms map[int]*RoomInstance`), completely eliminating raw array shuffling.

---

## 4. Concurrency & Thread Safety

- **Read-Only World Structure**: Once boot-parsed, the world map structure and room exit configurations are read-only and immutable. Players and ticks reading exit links can safely fetch references concurrently without requiring heavy thread-blocking locks.
- **Room State Isolation**: Thread safety for dynamic room states (like adding/removing items or characters to `RoomInstance` or toggling exits) is strictly enforced via dedicated mutex guards (`p.mu` / `w.mu`), avoiding race conditions during concurrent player movement.

## 5. Summary of Recommended Next Steps

1. **Leverage Modern Formats**:
   Since the online editor is deprecated, new zones could transition from legacy Diku `.wld` text formats to clean, structured YAML or JSON schemas, vastly simplifying area development for builders.
2. **Expose Room State via Web Admin**:
   A web-based admin interface could allow administrators to view, edit, and create rooms online via a secure REST API or visual UI, replacing the old command-line OasisOLC editor with a much safer, premium modern dashboard.
