## Lock audit

- **Weight arm:** no lock is held. `liveObjectsByID` snapshots under `World.mu`
  and releases it before the loop; each field read is the same lock-free
  instance access the surrounding activity loop already made, and `MudLog`'s
  own delivery takes `manager.mu`, player read locks and `World.mu.RLock` only
  after the snapshot is gone. No writer lock is held at the producer.
- **`canget` arm:** the engine is inside `RunScript`, so it holds `e.mu` (the
  scripting mutex, which serializes scripts as C's single-threaded engine
  does). No world, player, manager or lifecycle lock is held; the
  `CanCarryObject` query takes and releases `World.mu.RLock` internally. A
  shared read lock cannot deadlock against delivery's own `World.mu.RLock`, and
  nothing on the delivery path acquires `e.mu` — the scripting engine never
  calls `MudLog` while holding it in a way that re-enters a script.
