# Kill reward follow-up — 2026-10-29

The kill reward follow-up traced the live C `damage()` tail (`src/fight.c:1630-1712`) and the Go `HandleDeath` path. Three targeted scenarios were added for the reported recipient, autoloot-audience, and autogold cases. A fourth unit case exercises the durable save hydration boundary.

The ungrouped follower proof uses a passive grouped leader and a second passive grouped follower. With the fix, the ungrouped killer receives the solo XP line. Reverting `combatIsInGroup` routing to the `origin/main` member-count branch removes XP from the killer and awards shares to the grouped players, a repeatable R5h red. The autoloot proof kills through `kick`, observes the bystander, and matches the ordinary C `get all corpse` path. God `kill` was rejected as a fixture because C routes implementor kills through `raw_kill` and bypasses `damage()`.

The auto-gold command path itself already matches C on the current runtime fixture. The reachable defect is persisted preference hydration: V1 saves migrate `PRF_AUTOGOLD` and `PRF_AUTOSPLIT` bits, but the Go runtime mirrors were only restored from newer bool fields; contradictory V2 flags and bools also left the flags ignored. The focused `DeserializePlayer` regression test fails on `origin/main` and passes when the mirrors are rederived from migrated flags. No save fields or format changed.

Class audit — lethal paths and scope:

- `pkg/session/manager.go:SetDeathFunc` wires the engine `DeathFunc` to `World.HandleDeath` (`pkg/game/death.go`). The engine's normal `CombatEngine`/one-hit route therefore reaches the shared handler after a lethal common damage result.
- Direct World funnels also reach `HandleDeath`: `World.doDamage` (`pkg/game/damage_stubs.go`) covers offensive skills such as bash, kick, backstab, disembowel, ambush, neckbreak, and tiger/dragon kick; `World.DoSpellDamage` covers area damage spells; `World.ApplySkillDamageWithMessage` covers command-owned skill hits; and `pkg/spells.inflictDamage` (`pkg/spells/damage_spells.go`) handles `mag_damage`-style spell dispatch and invokes the world's `HandleDeath` after the common damage and position checks. The existing `pkg/spells/damage_spells_death_test.go` exercises that spell death callback. Fighter-special damage in `World.mobSkillDamageAfterGate` (`pkg/game/spec_fighter.go`) also explicitly calls `HandleDeath` when the victim reaches `PosDead`.
- Other damage-like code does not uniformly use the World reward handler: werewolf bite in `pkg/game/spec_procs3.go:790` calls `combat.TakeDamage` with the engine's default `DieWithKiller`/`RawKill` tail, while `specFieldObject` applies its own lethal effect and calls `w.rawKill` (`spec_procs3.go:845-851`). Room activity's croak attack also calls `RawKillCombatant` directly (`pkg/game/room_activity.go:164`). These special paths bypass this reward tail and remain outside this fix's proof.
- C's direct `raw_kill` callers bypass `damage()` and this reward tail by design. Go equivalents include the implementor `kill` command (`src/act.offensive.c:134-160`); instant-lethal spike/stake `SkillResult.RawKill` and command dispatch (`pkg/game/skill_combat.go`, `pkg/command/skill_commands.go`); disintegrate (`pkg/spells/affect_spells.go`); scripted Lua `raw_kill` (`pkg/game/world_bridge.go:455`, registered through `pkg/scripting/bindings_bridge.go`); gate backfire (`pkg/game/gates.go`); shooting (`pkg/game/shoot.go`); and the field-object special above. They must not be mistaken for ordinary damage kills. Lua's audited death binding is `raw_kill`; its `command` action routes player text through `CommandExecFunc` and mob text through `NPCCommand`, not through a separate Lua damage API.
- The ordinary C player attack tail is `src/fight.c:1630-1712`; it performs kill rewards and invokes autoloot after `attitude_loot` for a player killer (`src/fight.c:1691-1712`). The Go common death tail now mirrors that ordering and invokes ordinary `DoGet("all corpse")`, including when no corpse was produced. For player killers, the group check follows C `is_in_group(ch)` (`src/fight.c:637-654`) rather than treating any follow edge as membership. Group membership involving NPC actors remains an explicit unimplemented class gap: `combatGroupMembers` and `combatIsInGroup` are player-only, and `AwardMobKillXP` counts only player recipients as the divisor. Thus a mixed group such as a grouped PC leader plus grouped NPC killer/follower is not claimed to have C-equivalent XP division or recipient behavior. This PR avoids extending that unproven surface.
