## Runtime clock and reset serialization

C: src/structs.h:632; src/comm.c:805-808; src/db.c:1967-2045,2285.
World owns runtime age, minute accumulator and FIFO entries. Both live and
DP_CLOCK dispatch the same OnZoneUpdate every 100 pulses, after extraction.
Six calls advance ages in sorted zone-table order. Modes 0/1/2, sentinel 999,
blocked-head bypass and one reset per heartbeat follow C. Manual reset zeroes
age without removing queued entries; another minute can queue a duplicate
while the original remains blocked. There is no periodic reset goroutine.
Boot resets remain in table order. Updates before boot population completes
do nothing. The spawner is constructed before NewWorld returns, so its
pointer is stable for combat/death readers.

Proofs: TestZoneHeartbeatTenSecondBoundary fails on main (0 calls at pulse
100). TestZoneClockMinuteModesAndQueue observes a real D command and the
blocked queue. TestZoneClockManualResetPreservesQueue observes duplicate
entries and one-at-a-time service. TestZoneClockPumpedHeartbeatExecutesReset
pumps 599, 1, then 100 pulses: the second due zone's door resets at 700,
not 600. TestZoneClockConcurrentManualAndHeartbeat exercises the common
manual/admin entry against updates and snapshots under -race.

Assertion-failing controls are retained as fixed/reverted/restored logs
(0/1/0) under
~/Archives/darkpawns/oracle-runs/2026-10-02/dp-1371-zone-clock-proofs/:
heartbeat (restore 60-second interval), minute (age every seventh update),
mode0 (age disabled zone), mode2 (occupancy blocks unconditional reset),
age-zero (write sentinel after reset), one-reset (discard whole queue).
The exact control script is retained alongside the logs. Build failures
are not proof; each reverted log must contain a test assertion failure.

Other readers: wizard zreset and both admin route implementations use
World.ResetZone. Startup uses StartZoneResets. Direct Spawner.ExecuteZoneReset
also takes the same mutex; the internal executor avoids recursive acquisition.
Zone definitions and OLC edits remain parser data, replaced under World.mu;
runtime ages/queue do not alter them or persisted files. Future show zones
can use ZoneClockSnapshot. Global mob/object counts, RNG, rare initialization,
room snapshots, pending extraction and Lua lookup semantics are unchanged by
this train's executor wrapper. The unresolved command matrix remains explicit.
Spawner lookup/removal bookkeeping now takes its existing mutex because
public spawn/registration methods and combat cleanup also mutate those maps.
RegisterObjectInstance currently has test callers only; live restore uses
World object registration, not that spawner tracking API. P lookup ownership
remains part of the next command matrix. Mobile cleanup
runs after releasing that mutex; R mobile's deferred/order repair remains next.

## Lock acquisitions

No reset path acquires playerLifecycleMu. No new path nests Manager.mu and
World.mu. ZoneClockSnapshot takes zoneResetMu then a short World.mu read.

- Boot: zoneResetMu for the ordered pass, short World.mu read for definitions;
  internal executor uses the existing fine-grained Spawner/World/body locks.
- World.ResetZone (wizard and admin): zoneResetMu, World.mu read for definition
  lookup (released), then internal executor. The mutex is released before
  wizard acknowledgement, HTTP response and admin audit output.
- Direct Spawner.ExecuteZoneReset: zoneResetMu, then internal executor.
- Automatic update: zoneResetMu, short World.mu reads for definitions; occupancy
  snapshot (manager/send locks, released), body room locks, then World.mu reads
  resolving room zones; execute only after those snapshots are released.
- Executor: spawn acquires Spawner.mu then World.mu; global-count helpers use
  World.mu alone. P lookup uses Spawner.mu read. Tracking removals use
  Spawner.mu and release before World cleanup. Object movement/extraction,
  mob state and exit publication keep their existing fine-grained locks.
- Admin single-zone: Huma reset-zone and legacy handleZoneByIDOrReset hold no
  manager/lifecycle/world lock on entry to ResetZone. Audit/response follows it.
  Both reset-all handlers snapshot sorted zones and release World.mu before
  calling ResetZone for each entry; each reset independently takes zoneResetMu.
  The separate unimplemented dispatch endpoint remains unimplemented.
