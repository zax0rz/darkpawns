# DP-1371 E2-attr: boundary-based effective attributes

Base: `origin/main` at `00a698ded` (after #1732). Zach approved the shared
attribute repair in the goal brief's “Decisions added during Phase 4.”
This is its design-first PR. No implementation or new fidelity claim.

## Decision: explicit base and effective runtime views

Choose **recomputation at C's boundaries**, rather than always clamping on
read. This choice is required by a verified counterexample:
`do_restore` copies `real_abils` into `aff_abils` without calling
`affect_total` (`src/act.wizard.c:1604-1612`). Qualified immortal base
attributes become 25; effective DEX remains 25 immediately after restore.
The next `affect_total` bounds PC DEX at 18, regardless of level
(`src/handler.c:351-356`). A getter which always clamps PCs to 18 changes
C's restore behavior. A level-based exemption also changes C.

Retain existing serialized `Player.Stats` as the **base** (`real_abils`).
Add an unexported runtime effective-ability view corresponding to `aff_abils`;
initialize/copy/recompute it only where the traced C path does so. Use the
same bounds/conversion function for PC and NPC effective views. No save
field or database format change; neither read-time clipping nor rewriting
base values to hide a bonus.

The representation must distinguish these operations explicitly:

- base mutation followed by `affect_total`;
- base mutation followed by a direct base→effective copy (restore, creation,
  prototype initialization where C uses that copy);
- effective-only mutation, preserving its C lifetime until recomputation.

Existing tests that construct actors by assigning fields must use the same
initialization/copy boundaries as their intended C fixture. Production
writers must be traced rather than silently synchronized by getter magic.

## Recompute contract (R1/R3/R5e)

`src/handler.c:314-373` removes equipment modifiers, spell modifiers and
tattoo modifiers, copies base abilities, then reapplies equipment, spells,
and tattoo before bounding. The implementation will calculate effective
abilities from the same sources without mutating the permanent base;
non-ability state affected by those operations must retain C's ordering.
No RNG draw is added.

DEX/INT/WIS/CON: floor 0, ceiling PC 18 / NPC 25. STR: floor 0; NPC ceiling
25; PC STR above 18 converts to ADD using existing base ADD plus
`(STR-18)*10`, capped at 100, then STR becomes 18. Do not cap CHA. Clamp
alignment at the recomputation boundary to ±1000. Do not repeatedly convert
an already-effective ADD or permanently lose bonuses on removal.

## Audit findings and implementation obligations (R5c)

The checked-in search inventories conservatively include field references,
base copies, getters, and attribute-like fields of unrelated types. They are
**candidate sites, not a claim that all are effective reads**:

- [Go Stats/getter sites](../evidence/2026-09-30-e2-attr/go-attribute-sites.txt)
- [Go direct fields](../evidence/2026-09-30-e2-attr/go-direct-attribute-fields.txt)
- [C ability and boundary sites](../evidence/2026-09-30-e2-attr/c-attribute-sites.txt)

| Family | Current representation | Required disposition |
|---|---|---|
| Combat/stat getters | PC sums base + spell + equipment at read; NPC reads instance fields | Return effective view; use shared C bounds at traced boundaries |
| SQLite conversion and character creation | Copies Player.Stats | Preserve base serialization; initialize effective view at the C lifecycle point |
| Equipment | PC modifiers are folded at read | Trigger recomputation after successful equip/unequip; notify outside equipment locks |
| Spell affects | PC ActiveAffects; NPC CustomData affect records | Recompute on add/join/remove/expiry; preserve list and callback order |
| Tattoo | Two live implementations mutate stat fields: game.TattooAf and session.tattooAf | Centralize modifier application; preserve old-tattoo removal before new-tattoo addition, avoiding base drift/double application |
| Level gains and inventory capacity | Several reads directly use Player.Stats | Trace each C base/effective use; route effective consumers through the effective view without recursive player locking |
| Communication, observation, Lua table fields | Some read base fields directly | Classify each boundary against C; fix effective reads, retain explicitly base-only data views |
| Wizard restore/set, remort, permanent constitution changes | Mix direct writes and base adjustments | Separate copy, recompute and effective-only operations by actual C call path |
| Deprecated engine.AffectTotal | Getter/setter-based helper; removes/readds without restoring a separate base; not the live actor path | Do not activate it as the repair; keep legacy API tests separate from live parity claims |

The important boundaries were verified in `src/handler.c:395,419,437,748,792`
(affect add/remove and equipment) and `src/scripts.c:1302,1379` (save_char and
set_skill). Tattoo's exact modifier table and remove/add behavior were read
in `src/tattoo.c:104-195`. The session tattoo implementation is reachable
from `pkg/session/wiz_set.go:717-721`; the game implementation has death,
remort and tattoo acquisition callers. Treating tattoo as permanently
modified base would break removal restoration.

These sites establish that this is an L-sized runtime-representation change
with real design choices, rather than a five-getter clamp. The goal brief
requires: “Design-first batches (C1, and any batch you judge L-sized with real
design choices): first open a short design-note PR (docs only) and stop.
After it's approved, implement.” This PR follows that instruction.
