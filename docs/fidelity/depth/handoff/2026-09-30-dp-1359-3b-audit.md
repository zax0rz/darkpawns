## Creation record and hometown

C accepts the roll with `init_char` and `save_char` before MOTD
(`src/interpreter.c:2125-2129`). On entry it runs `reset_char` and saves before
`do_start` (`:2175,:2186,:2214-2216`). `reset_char` raises nonpositive current HP
to one (`src/db.c:2957-2958`). `do_start` gives the kit first
(`src/class.c:499-533`), sets level/experience and base maxima, initializes
starting skills (`:535-570`), calls `advance_level` (`:572`), which saves at
`:712`, and only then refills pools (`:574-576`), sets conditions/preferences
and wimp (`:578-589`), grants two practices (`:590`) and sets original
constitution (`:591`). The kit's `obj_to_char` calls set PLR_CRASH
(`src/handler.c:569-571`), so that bit is already in the advance-level record.

Go's constructor pre-applies final do_start defaults. `creationRecord`
materializes C's phase on a separate, draw-neutral restored character, without
undoing those defaults on the original live character. SQLite is written at
accepted-roll, pre-do_start entry, and post-advance/pre-refill boundaries. No
final creation save overwrites the intermediate record. The snapshot includes
C's kit-induced crash flag without moving Go's actual kit operations. Starting
skills now precede the advance save, as in C. Accepted-record menu resume
reconstructs the same initial live defaults before advancing; body draws are
not repeated.

| Phase, ordinary warrior with wisdom 12 | level | current/max HP | practices | orig_con | conditions | preferences |
|---|---:|---|---:|---:|---|---|
| Accepted roll / init_char save | 0 | 0/0 | 0 | 0 | 24/24/24 | before do_start defaults |
| Menu entry / pre-do_start save | 0 | 1/0 | 0 | 0 | 24/24/24 | before do_start defaults |
| advance_level save | 1 | 1/rolled maximum | 2 | 0 | 24/24/24 | before do_start defaults |
| Initial live character | 1 | full/rolled maximum | 4 | rolled constitution | 36/36/0 | display flags, autoexit, wimp 5 |

Practices depend on C's class/wisdom tables; two in the advance record is the
chosen fixture, not a universal constant. The first-player God skips do_start;
its existing initial live state and draw count remain unchanged.

Hometown was not a creation bug: `char_creation.go` already retained the chosen
home, and SQLite stores it. C sets GET_HOME in CON_HOMETOWN
(`src/interpreter.c:2096-2100`) and copies it in both directions
(`src/db.c:2433,:2597`). The old sidecar serializer omitted hometown, causing
stat file's zero. SQLite restores the actual selected value, without migration.

`GetOrigCon` used to substitute rolled constitution for zero at every read.
C's GET_ORIG_CON is the field itself. C applies the sanity assignment only at
world entry, **after** the entry save (`src/interpreter.c:2232-2233`). The getter
now returns zero faithfully, and returning entry performs that assignment at
C's boundary. Its two production consumers were audited: the stat renderer and
constitution seller (`src/spec_procs3.c:269-277`, GET_ORIG_CON minus real_abils.con).
The seller's focused test now expects an explicit zero to remain zero; real
entered players get the entry sanity assignment.

## Offline set: session fields, identity and concurrent saves

Each file command loads the current SQLite record, materializes the player,
applies the C field, and converts it back. OLC is retained from that record
unless the OLC field was explicitly edited (`src/act.wizard.c:3003`). The load
room is retained: C's file path calls char_to_store directly, rather than the
live save_char(NOWHERE) override. Password/authentication fields are not replaced
by the ordinary player update. File saves reset base armor/hitroll/damroll as char_to_store does (db.c:2608-2610), with TestSetFileSQLiteCombatBase. Explicit password edits use UpdatePassword and
bcrypt; explicit name edits atomically update the existing name column with the
player record, corresponding to C's name/index update at :2889-2895.

`SavePlayerIfCurrent` compares every column it replaces, plus name, in the same
SQLite UPDATE. A newer save causes a conflict and leaves that newer record
untouched; there is no check-then-write race or timestamp granularity reliance.
Clan offline edits use the same compare-and-save boundary and preserve OLC.
Offline edits retain the original inventory/equipment bytes: C’s char_to_store does not write its separate crash-object file. Clan listing materializes metadata without restoring objects. There are no new columns, format versions or payload keys.

C's password refusal applies to **non-file** set (`src/act.wizard.c:2973-2978`):
“You must use set file…” and “The player *must* not be logged in…”. File mode
instead prints the warning at :2986-2987 and writes the password at :2988-2989.
The higher/equal-level file target gate retains C’s Orodreth/Serapis exemptions (:2656-2664). No blanket online-file prohibition is invented. A file edit updates the record,
not a same-named live session; the online saver still rejects foreign pointers.
