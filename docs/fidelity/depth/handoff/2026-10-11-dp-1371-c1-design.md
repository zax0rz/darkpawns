# DP-1371 C1 design note — character-aware command dispatch

Status: Zach approved the reviewer recommendation in this chat on 2026-10-11
("approve, this is great"). Bounded implementation slices are authorized;
generic C1 completion still requires the proof matrix below. The design note
and implementation will be retained in Git after the required gates run.

## Reviewer recommendation for Zach's decision

Approve the shared-dispatch fidelity route with incremental command coverage,
subject to the following concrete implementation boundaries:

1. Keep the command registry and interpreter orchestration in `pkg/session`.
   Reuse the existing C-table prefix resolver and command metadata; do not add
   a second mobile command table or move the player handler registry.
2. Use a session-local context containing the actual `combat.Combatant` body
   and an optional real `*Session`. Wire a character callback from game to
   session using the body and original input line. No fake Player or Session.
   `Combatant` supplies common body operations, but does not expose numeric
   identity, flags or equipment; obtain those from the actual Player/Mob types
   through explicit actor helpers rather than assuming the interface has them.
3. Preserve existing player entry adapters and callback behavior during the
   first slice. Audit the existing callback's order, combat and Lua callers
   before changing its signature or routing. Extract shared resolution, gates
   and dispatch without changing player alias, moderation, raw-text or
   empty-input behavior. Direct NPC entry consumes the leading C draw exactly
   once, including empty input. The known player blank-line RNG discrepancy
   remains a separately reported fidelity gap, not an approved divergence.
4. Preserve currently supported NPC say/tell/emote/give/social behavior while
   routing supported handlers through common metadata. Add faithful sit/stand
   handlers, including position and mount branches. Do not drop existing
   command support to make the first slice smaller. Unsupported command
   outcomes remain explicit in internal dispatch results and the coverage
   inventory; they never produce invented player messages or completion claims.
5. Native specials are part of the design, not an existing reusable NPC hook.
   `SpecFunc` and `ObjSpecFunc` in `pkg/game/spec_assign.go` currently take
   `*Player`, and `COrderedWorn`/`COrderedCarrying` in `pkg/game/item_views.go`
   also take `*Player`. Audit their definitions, registrations and readers,
   then implement real actor support in reviewed slices. Preserve C order and
   first-true semantics, including native equipment/inventory specials and
   the room-object oncmd stage which is not gated on player status. Never
   pass nil or a fabricated Player to a player-only special to claim coverage.
6. Keep player-only private output attached to real descriptor ownership;
   descriptor-less NPCs still perform canonical room acts and state mutations.
   Preserve actual switched-player routing rather than assuming every NPC
   lacks a descriptor. Test nested Lua action/special dispatch for context
   restoration and lock behavior before using the shared path in the bridge.
7. First implementation is a stop-tier train. It may prove visible-NPC force
   targeting with sit/stand, but the generic force and Lua interpreter rows
   remain blocked until the documented resolution/gates/specials/RNG/handler
   matrix is proven. Each later command family extends that same dispatcher.

This approval authorizes the architecture and bounded implementation
slices, not closure of all three C1 rows. No oracle, governing-document or
transport-policy changes are part of the approval. The design-note PR is
docs-only; Zach has approved the design directly in this chat before that PR.

## Problem and C contract

C has one command interpreter for a `char_data`, regardless of whether the
character is a player or a mobile. `do_force` resolves a visible character and
calls `command_interpreter(vict, to_force)` (`src/act.wizard.c:1862-1880`;
`src/handler.c:1303-1323`). Lua `action(me, line)` makes the same direct call
(`src/scripts.c:122-139`). The interpreter draws `number(0,3)` and clears
`AFF_HIDE`, parses the command, performs ordered prefix lookup and gates,
offers the command to `special()`, then invokes the handler
(`src/interpreter.c:883-949`). `special()` itself has ordered room, equipment,
inventory, mobile, and room-object stages (`src/interpreter.c:1407-1480`).

The two force rows are linked but separate claims: `force.visible-npc-target`
proves NPC target resolution and the force handoff; `force.npc-command-interpreter`
proves generic command semantics. `lua.npc-command-unported` shares the latter
boundary. A green force `sit` alone cannot prove the interpreter class.

Go currently has a player-only force executor (`pkg/session/wiz_communication.go`)
and a separate `World.NPCCommand` whitelist (`pkg/game/npc_command.go`). The
world resolver can return a `MobInstance` (`pkg/game/target.go:145-193`), but
`findForceSession` discards any target without a player session. Lua's game
bridge routes NPC `action()` to that whitelist and players through
`CommandExecFunc` (`pkg/game/world_bridge.go:352-362`). The session command
path contains the player registry, ordered C prefix lookup, gates, specials,
and handler calls (`pkg/session/commands.go:560-778`); its current gate and
special helpers require `*Session` (`:792-815`, `:832-875`).

## Recommended ownership and interfaces

Keep the interpreter orchestration in the session/command layer, where the
authoritative Go command registry and existing player handlers live. Do not
make `pkg/game` import `pkg/session`: the game already exposes callbacks for
commands because session depends on game. Extend that callback boundary to
accept a character body, then wire it from `session.Manager` to a
character-aware dispatch entry point. Force and Lua both call that boundary;
they do not implement a second parser or whitelist.

The dispatch context should carry two distinct things rather than pretending a
mobile is a `Player` or a `Session`:

```go
type CommandActor interface {
    combat.Combatant // body identity, level, position, room, and NPC status
    // Narrow command-specific facets are added only when C handlers require them.
}

type CommandContext struct {
    Actor   CommandActor
    Session command.SessionInterface // nil for a descriptor-less mobile
}
```

This is an interface sketch, not an approved signature. `combat.Combatant`
already captures body identity, level, position, room, and NPC status. The
context must not synthesize `Player` fields or a session for a mobile. A nil
session means descriptor-owned `send_to_char` output has no recipient; it must
not redirect those bytes to the room. Room acts and state changes still use
the real `MobInstance`. The reviewer recommendation uses an optional real session in a session-local
context; descriptor-less output must not be redirected to observers.

Preserve `executeCommandRaw` as the player-facing entry adapter. It retains
transport processing, moderation, alias expansion rules, guest restrictions,
metrics, raw argument preservation, and current session behavior. Normal player
input and direct C-style calls enter the shared interpreter kernel through
separate entry profiles, since only normal transport input has transport
preconditions. The kernel owns the shared sequence for inputs that reach it:
one hide roll before parsing, C command-name tokenization, ordered level-aware
prefix lookup, frozen/not-implemented/NPC-immortal/position gates,
`special()` consumption, then handler dispatch. Direct force and Lua calls do
not expand aliases, matching their direct C calls to `command_interpreter`.
Today's `executeCommandRaw` also runs Go moderation checks; preserve that
behavior for existing player force until any policy change is separately
authorized, while the new descriptor-less NPC entry must not accidentally
acquire transport-only moderation or guest filters.

There is a specific empty-input boundary. C `process_input` stores each parsed
line, including an empty line, in the input queue (`src/comm.c:1961-2008`);
`game_loop` calls `command_interpreter` whenever `get_from_q` returns a queue
item (`src/comm.c:597-628`; `src/comm.c:1232-1248`). Thus a player pressing
Enter on an empty line reaches C's interpreter and consumes its leading draw
before C returns (`src/interpreter.c:889-895`). Go `executeCommandRaw`
currently returns after `splitCommandInput` when the command is empty, before
its draw (`pkg/session/commands.go:585-590,643-649`). This design preserves
that existing transport-adapter behavior; changing it is outside this C1
proposal and would need separate authorization and proof. The direct
character-aware entry used by force/Lua must still draw before its empty-line
return, as C does. Do not present a player-versus-NPC empty-line comparison as
proof of parity; the transport empty-line difference remains explicit and
unresolved.

`runSpecials` needs an actor-aware form rather than a fake session. Preserve
C's first-true order and NPC-specific script gates. Native specials receive
the actual body. For C's `!IS_NPC(ch)` oncmd stages, a mobile skips the same
stages C skips; room and object/mobile native specials still receive the
mobile. Current Go `runSpecials` models switched sessions, not descriptor-less
mobile inventory/equipment, so this requires a source-order audit before
implementation. Do not reuse its switched-player assumptions without proof.

Dispatch handlers through two explicit lanes: existing `*Session` handlers
remain the player lane and keep their current implementations; character-native
handlers accept `CommandActor` and have no session requirement. The newly ported NPC-native command set starts with `sit` and `stand`, the
safe force vehicle pair; existing supported NPC handlers remain available. C's `do_stand` and `do_sit` own position-dependent
private and room acts (`src/act.movement.c:696-755`). Go's current `NPCCommand`
has a `stand` branch and helper, but that helper is simplified relative to the
C handler; it has no `sit` branch. Both commands therefore need actor-native
handlers that preserve the relevant C branches and are reached through common
resolution/gates/specials, not a force special case. Existing NPC helper
behavior for `say`, `tell`, `emote`, `give`, and socials can be retained behind
explicit character-native registrations only after the shared path preserves
their current output and state behavior; their presence in the old switch does
not prove generic dispatch.

This first handler set does not make every registered C command mobile-capable.
A command that resolves in C but has only a player/session handler must remain
unsupported for the mobile lane and its relevant fidelity case blocked until a
body-safe implementation and proof exist. The shared kernel must not silently
consume such a command, map it to a similarly named helper, or emit a Go-only
warning to players. Keep `force.npc-command-interpreter` and
`lua.npc-command-unported` blocked if the implemented/proven command matrix is
only this starter set; do not mark generic NPC dispatch complete based on
`sit`/`stand` alone. Additional command families can advance behind the same
kernel in later bounded slices.

## Behavioral invariants

- Player input continues through the same `executeCommandRaw` adapter and
  existing session handlers. Extracting the shared kernel must not alter
  player bytes, command order, gates, alias handling, or random draws (R1/R2/R3).
- Every direct character-aware interpreter invocation, including empty or
  unknown input, consumes exactly C's leading hide draw; on zero it clears hide
  on the actual actor. The transport player adapter's current empty-line early
  return is preserved as an explicit unresolved difference. The player test
  seam and deterministic stream remain usable. NPC draw parity needs its own
  fail-capable assertion (R3a/R3d/R5h).
- Command resolution keeps C table order and level filtering during prefix
  lookup. C runs `special()` only after lookup and refusal gates; the resolved
  command name and original remainder passed to a special must retain current
  semantics (R2/R5e).
- Private refusal and command messages to a descriptor-less NPC have no
  audience. A command can still mutate the mobile and produce canonical room
  output. Do not turn private output into room text (R1/R4).
- Force remains the caller: C sends its actor acknowledgment, applies its
  existing victim notice rules, logs in current order, and invokes the generic
  interpreter. The NPC work must not change player force output or room/all
  filters. Lua `action()` remains a direct command-interpreter caller, not a
  transport command (R1/R2/R5e).

## Proof plan

Keep `force.visible-npc-target` and `force.npc-command-interpreter` as separate
manifest rows. Cover, with paired C/Go scenarios and focused unit assertions:

1. Force a visible NPC to `sit` and `stand`; assert caster acknowledgment and
   exact room output, and assert no private NPC output leaks to a player.
2. Exercise an NPC command rejected by its position gate, an abbreviated
   command name, a native special that consumes the command, and a command
   outside today's whitelist. Show which effects/messages occur for peers and
   which descriptor-only bytes disappear.
3. Prove NPC leading-draw behavior on empty, unknown, and valid lines, and
   prove the selected hide effect on the actual mobile. Separately prove
   player and NPC draw parity on a nonempty line that reaches both interpreters.
   Do not change or claim the existing Go transport empty-line behavior here.
4. Exercise Lua `action()` through the same dispatch boundary so it cannot
   retain a separate whitelist path. Keep D7's Lua persistence/WHOD/mudlog
   evidence and implementation ownership separate.
5. Add a mutation control that disables the common handoff and fails on an
   assertion. Each new proof must fail for the behavior it claims, not merely
   on compilation or timeout (R5h).

The Phase 4a proposal asks for both oracle and unit matrices for these branches.
`force-mob` is the existing safe oracle vehicle; retain `--show-oracle` evidence
when implementation is authorized. A change to player-visible or game
behavior is stop-tier and needs the census and repository gates required by
the governing workflow. This design-only note requires no census.

## Alternatives and unresolved decisions

1. **Shared interpreter kernel with two actor lanes (recommended):** reuse the
   existing player adapter and handlers while adding a real character context
   and explicit mobile-capable handlers. This preserves current player code
   and gives force/Lua one generic handoff. The design review must settle
   whether the registry belongs in `pkg/session` with an injected callback or
   moves to a lower-level package; moving it risks broad handler churn.
2. **Move all command registration and handlers into a new neutral package:**
   offers a clear owner for the interpreter, but current handlers depend on
   `*Session`, `*Player`, and manager state. This is a larger migration and is
   not justified unless option 1 cannot avoid duplicated policy.
3. **Keep the whitelist and route force into it:** smallest code change, but
   leaves command lookup, specials, and the rest of C's reachable NPC command
   surface absent. It is not a C1 parity solution. Keeping it as the final
   contract would require Zach's explicit divergence approval and fail-capable
   tests; no such approval is assumed here.

Before implementation, decide the callback signature and ownership, the
descriptor-less output representation, whether `say`/`tell`/`emote`/`give` and
socials join `sit`/`stand` in the first character-native slice, and how
actor-aware equipment/inventory specials are surfaced without widening the
core actor interface. Resolve whether the current player-force moderation
check is intentionally retained on the direct shared entry or remains in its
player adapter; no policy change is proposed here. The existing Go empty-line
transport difference is explicitly left for a separate decision. Audit command
handlers that currently mutate player-only persistence or session state; a nil
session must not trigger guessed behavior. Keep the shared `CommandExecFunc`
change coordinated with any owner touching `WorldScriptableAdapter.Command`.
