# DP-1313 — the live board pile-up was the removed world-state replay

DP-1313 reports the Temple of the Cross gaining boards on the live server:
9 after one restart, 13 after another, on the same database. The fresh-world
reset already matches C (PR #2704's `board-temple-reset-depth`); this note
finds the live step in git history.

## The step

Before commit `d4b3298c7` (2026-09-26, "fix(fidelity): reset transient world
state on restart"), the Go server replayed a `data/world_state.json` snapshot
at boot. `cmd/server/main.go` called `game.LoadWorld` after the world boot,
and `pkg/game/save.go`'s `DeserializeWorld` appended every saved room item:

```go
for roomVNum, refs := range sd.RoomItems {
  for _, ref := range refs {
    obj := NewObjectInstance(proto, roomVNum)
    obj.ID = w.nextObjID
    w.objectInstances[obj.ID] = obj
    w.roomItems[roomVNum] = append(w.roomItems[roomVNum], obj)
  }
}
```

That append ran **after** the boot zone resets and did not consult the reset
maximum, so each restart added the previous run's ground boards on top of the
boards the `O 0 8099 5 8008` reset had just placed. The restored objects were
registered, so `countObjectInstances(8099)` and the room contents agreed — the
count-versus-room probe cannot see this step; the defect is the replay itself
bypassing `src/db.c:2149-2150`.

## The fix already landed

`d4b3298c7` removed the replay. `pkg/game/world_state.go` now only reports a
leftover snapshot (`IgnoreLegacyWorldState`) and never reads it into the world;
`pkg/game/save_world_test.go` pins that contract
(`TestIgnoreLegacyWorldStateIsNotFatalAndKeepsTheFile` and the inspection
tests). The live check on 2026-10-15 found one board, consistent with the fix.

## Current verification

- PR #2704's `board-temple-reset-depth`: seven `zreset 80` cycles on a fresh
  world keep the same board count in C and Go (draw parity MATCH).
- This session also ran the reset against room 8008 and confirmed the `O` cap
  is world-wide in both engines.
- A restart on the same SQLite database cannot reproduce it on current main:
  the player store does not persist room contents, and the snapshot is not
  replayed.

## R5b — the class

The replay affected **every** `O`-loaded zone object, not just the board: any
ground object saved in `RoomItems` was re-added after the reset cap had run.
Boards were merely the visible instance because the Temple board line has a
max of 5 and players notice duplicates. The removed replay covers the whole
class.

## Conclusion

No code change is needed on current main. DP-1313's live step is explained by
the removed snapshot replay; the current code matches C and the regression is
covered by the existing `world_state.go` tests plus the #2704 reset witness.
