## What the C Source Does

C's CON_MENU is the state after MOTD where the player picks what to do next. It applies to BOTH new characters (after `do_start`) AND returning characters (after crash_load). The menu text is in `src/config.c`:

```
Welcome to Dark Pawns!
0) Exit from Dark Pawns.
1) Enter the game.
2) Enter description.
3) Read the background story.
4) Change password.
5) Delete this character.

   Make your choice:
```

**Reference:** `src/interpreter.c` lines 2165-2355

### Option 0 — Quit
Closes the connection. Simple.

### Option 1 — Enter the game
The normal path. For returning characters: loads saved equipment, sets load room, sends welcome message, enters world. For new characters: already handled by `completeCharCreation()` in Go.

### Option 2 — Enter description
Opens a text editor where the player writes a multi-line description that other players see when they `look` at them. In C this uses the string editor (CON_EXDESC state). The description is stored in `ch->player.description`.

In Go: `Player.Description` field already exists (player.go:172). But the DB `players` table does NOT have a `description` column. You'll need to add one (VARCHAR or TEXT).

### Option 3 — Read background story
In C this pages the `background` string (loaded from a file at startup) then returns to CON_MENU. In Go, this could read from the world data or just show a hardcoded/fetched story page. Returns to menu after reading.

### Option 4 — Change password
C flow:
1. Prompt "Enter your old password:" (echo off)
2. Compare with stored hash → if wrong, show error, return to menu
3. Prompt "Enter a new password:" (echo off)
4. Validate: min 3 chars, max MAX_PWD_LENGTH, not equal to character name
5. Hash new password, store
6. Prompt "Please retype password:" (echo off)
7. Compare with new hash → if mismatch, restart from step 3
8. On success: "Done." + save + return to menu

In Go: Password hashing uses bcrypt (NOT C's DES crypt). `hashCharPassword()` in char_creation.go shows the pattern. `db.UpdatePassword(playerID, hash)` already exists. For comparison, use `bcrypt.CompareHashAndPassword()`.

### Option 5 — Delete character
C flow:
1. Prompt "Enter your password for verification:" (echo off)
2. Compare → if wrong, show error, return to menu
3. Show character name + "YOU ARE ABOUT TO DELETE THIS CHARACTER PERMANENTLY. ARE YOU ABSOLUTELY SURE?"
4. Prompt "Please type \"yes\" to confirm:"
5. If "yes" or "YES":
   - If frozen, refuse ("the ice stops you"), close connection
   - Set PLR_DELETED flag (or just delete — Go doesn't have C's flag system)
   - Remove from clan if applicable
   - Save character
   - Delete crash/rent file (Go: skip this, no crash files)
   - Log deletion
   - Close connection
6. If anything else: "Character not deleted." + return to menu

In Go: No `DeletePlayer()` function exists yet. Build it — either hard DELETE from players table, or soft-delete (add a `deleted` boolean column). Soft-delete is safer. Also remove from the in-memory world.

### Default — invalid choice
Show "That's not a menu choice!" + re-display menu.

## Architecture Decision: Menu State

The current char creation flow uses `s.charStage` (a string) and `handleCharInput()` to route input. The CON_MENU should be a NEW state that sits OUTSIDE char creation — it applies to returning players too.

**Recommended approach:**
- Add a `menuStage` field to Session (or reuse an existing state pattern)
- After MOTD in char creation (new chars): instead of calling `completeCharCreation()` immediately, show the CON_MENU
- After login for returning chars: show MOTD, then show CON_MENU
- When player selects option 1, THEN call `completeCharCreation()` (new) or the existing enter-world logic (returning)

**Alternative:** Extend `charStage` with menu stages (`"menu"`, `"menu_chpwd_old"`, `"menu_chpwd_new"`, `"menu_chpwd_confirm"`, `"menu_exdesc"`, `"menu_del_confirm"`). This keeps all the state routing in one switch. Simpler but conflates creation with post-creation menu.

**Go with whichever is cleaner — you have the codebase context.** The key constraint is that the menu must work for both new and returning characters.

The client already handles `char_create` type messages with options rendering (fixed in PR #234). The CON_MENU can reuse this message type:

      {"Key": "3", "Label": "Read the background story"},

Or just use the `text` type with the menu as plain text. Either works — the `char_create` type gives the client structured options to render nicely.

**Password entry needs echo-off handling.** Currently the client masks password input during login (`awaitingPassword` state). The menu's password change flow needs similar masking. Consider either:
- Adding a new message type like `char_create_password` that tells the client to mask input
- Or reusing the existing `text` type with a flag in the data payload

## What NOT to Do

- **Don't implement the C string editor (CON_EXDESC) as-is.** C's editor is a complex state machine with save/abort buffers, line editing, etc. For now, a simpler multi-line input mode is fine — read lines until the player types `@` or `/s` to save, `@` or `/a` to abort. Match the C editor's control commands if possible, but don't let perfect be the enemy of good.
- **Don't add crash/rent file handling.** Go doesn't have C's crash/rent system. Skip `Crash_delete_file()` and `Alias_delete_file()` from the delete flow.
- **Don't implement C's PLR_DELETED flag system.** Either hard-delete or use a simple `deleted` boolean.
- **Don't use DES crypt for passwords.** Go uses bcrypt. Use `bcrypt.CompareHashAndPassword()` and `bcrypt.GenerateFromPassword()`.
