# 2026-10-13: The 1997 game could load a mob; our oracle couldn't

## Scope

- **Tracks:** legacy-port fidelity (oracle validity, platform drift)
- **Window:** diagnosed 2026-10-13
- **Primary artifacts:** `~/Archives/darkpawns/oracle-runs/2026-10-13/load-mob-diagnosis/` (gdb backtrace, reference and candidate transcripts, both binaries with `SHA256SUMS`, `MANIFEST.md`); `src/act.wizard.c:123-126, 1304-1310`; oracle seam commit `7e08d59` (branch `claude/moblimits-64bit`); Go commit `af026ed76` (branch `claude/load-mob-success`)
- **Status:** verified. The crash, its cause and the repaired transcripts are all reproduced from retained artifacts.

## What was observed

`load.mob-success` had been blocked since 2026-10-06. Three honest C-first vehicles (numeric mobs 2100, 2109 and 1, plus a named `puff`) got **empty C blocks**, and a later note recorded that `load mob 4` "ends the C actor connection with EOF". The C source clearly prints on that branch (a gesture, a random load message, two creation acts), so the row stayed blocked rather than inventing bytes.

Running the reference binary under `gdb` showed the C server wasn't printing nothing. It was dying: `SIGSEGV` in `do_load` at `src/act.wizard.c:1305`, on every successful `load mob`, before any output. The cause is two lines:

```c
load_limits *MobLimits = NULL;                               /* :123 */
int num_moblim = sizeof (MobLimits) / sizeof (load_limits);  /* :126 */
```

The idiom `sizeof(array) / sizeof(element)` counts an array's elements. But `MobLimits` is a **pointer**, its only entry (Puff) commented out, so the expression divides a pointer's size by an 8-byte struct of two `int`s:

| Platform | `sizeof(MobLimits)` | `num_moblim` | `load mob` |
|---|---|---|---|
| The game as shipped, 32-bit Linux (1990s) | 4 | 4 / 8 = **0** | the limit loop never runs, works |
| The reference oracle, 64-bit Linux (2026) | 8 | 8 / 8 = **1** | reads `MobLimits[0]` through `NULL`, segfault |

The sibling `ObjLimits` is a real array, so `load obj` was never affected, and no other `sizeof/sizeof` in `src/` divides a pointer. Players in 1997 could load mobs without trouble. Our "ground truth" could not.

## The repair

Oracle seam `7e08d59` pins `num_moblim = 0`, the value the 32-bit build computed, with a comment citing both platforms. Before patching, a clean `-O0 -fcommon -ffile-prefix-map` build of the unmodified seam reproduced the reference SHA-256 (`4c421a01…`) exactly, so the candidate (`b5616234…`) differs only by this line.

On the candidate, `load-depth` (which now loads mob 1 and mob 4 by number and Puff by name) is green on seeds 1, 2, 3, 5 and 8. C reaches the gesture, `random_load_msg` (two loads drew different messages, and Go matched both, so the draw is proven too), both creation acts for actor, peer and observer, and the mobs appear in the room. Against the current reference, the same scenario fails with EOF after `load mob 1`, so the proof can fail (R5h). Mob 4 turns out to be "the remorter".

## Why it matters for the fidelity paper

1. **The oracle is an artifact of its platform, not the game.** The differential method treats the C binary as ground truth, but the C we compile today isn't the C that ran in 1997: the pointer width changed underneath it. This is the second platform-drift class the project has met. The first was optimization level: the `-O2` reference silently altered bytes through undefined behaviour (corrected 2026-09-28, which also resolved `wiznet @` today). Pointer width is a different axis. The code is well defined on each platform but means different things on each.
2. **"Blocked" was the honest state, and "a green must be able to fail" found the cause.** The vehicles reached a C branch that should print and got nothing. Rather than declare Go correct or invent bytes, the row stayed blocked until someone asked *why* C was silent. The answer moved the defect from the port to the reference.
3. **The repair restores the original platform's value instead of fixing the bug.** The seam doesn't "correct" the idiom to count a real array. It pins the number the shipped game actually used, which is the fidelity target. The distinction matters: fixing the C would be invention (R4), and pinning the historical value is restoration.

## Open
