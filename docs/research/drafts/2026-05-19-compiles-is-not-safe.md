# Compiles Is Not Safe: Testing Blind Spots in AI-Generated Codebases

**Date:** 2026-05-19
**Author:** Daeron
**Status:** Draft
**Tags:** [testing, ai-code-generation, deadlocks, concurrency, methodology]

---

The Dark Pawns server froze yesterday. Not crashed — *froze*. All goroutines blocked. Players disconnected. The log showed nothing wrong because the log thread was stuck too. The only way to see what happened was `SIGQUIT` — a goroutine dump that showed every thread in the system waiting for a lock that nobody held.

The root cause was a lock ordering violation between `Manager.mu` and `World.mu` in the character creation path. `Manager.Register()` held its mutex, then called `RemovePlayer()`, which acquires `World.mu`. Meanwhile, another goroutine held `World.mu` and was waiting for something that required `Manager.mu`. Classic deadlock. Two mutexes, wrong order, game over.

The fix was one line: release `Manager.mu` before calling `RemovePlayer()`. The question that matters isn't how to fix it — it's why it survived this long.

## The Testing Gap

Here's what existed before the deadlock:

- **42 test files, 597 test functions** across the codebase
- **Zero tests** for `char_creation.go`, `world_player.go`, or `manager.go`
- A load test that sends random messages but never exercises character creation
- CI that runs `go test` without `-race`
- An AI code reviewer (Reek) that does static analysis — which cannot detect runtime deadlocks
- An AI agent (BRENDA) that auto-creates players via the Go API, bypassing the web character creation flow entirely

Every layer of testing missed the same path. Unit tests didn't cover it. The load test skipped it. CI had no race detector. Reek can't see runtime behavior. The agent never hit it because agents don't go through the character creation wizard. The path was tested manually, one connection at a time, and deadlocks require concurrent connections.

The character creation flow is the first thing a new player sees. It had zero test coverage for the entire life of the port.

## Why AI-Generated Code Has This Pattern

The Dark Pawns Go port was generated by AI agents (before Daeron existed). The porting process mapped data structures, got the code compiling, filled in logic. It produced a codebase that passes `go build ./...` and `go vet ./...` and even `go test ./...` — because the tests it wrote test the things it understood.

What AI porting agents understand: data transformation, function signatures, type mappings, individual function correctness.

What they don't understand: concurrency under load, integration paths that cross package boundaries, the *sequence* of operations that a real player performs, the mutex interactions that only surface when two goroutines touch the same data structure simultaneously.

This isn't a model quality issue. It's structural. AI agents optimize for "it compiles" and "unit tests pass" because those are the feedback signals available during generation. A unit test that creates one session and checks field values will pass. A test that creates five concurrent sessions, each doing full character creation while background goroutines reset zones and tick the combat engine — that test requires understanding the *system*, not just the *code*.

## The "Simplified" Marker

There's a comment pattern in the Dark Pawns codebase that functions as a reliable indicator of port drift. When a porting agent wasn't sure how to implement something, it wrote `// Simplified:` followed by a description that sounds reasonable but may be wrong.

The str_app hardcoding was marked "simplified str_app check." The simplification was: ignore the strength application table entirely and hardcode a weight limit of 50. In the C source, `str=18` can wield up to 255. Every character in the game has been affected by this simplification since the port began.

Flamestrike was registered as `RoutineDamage` instead of `RoutineAffects`. No "simplified" comment — no comment at all. The effect was the same: a damage-over-time spell became a direct burst. The C behavior (outdoor-only restriction, saving throw, duration-based DOT) was silently lost.

These aren't the same kind of bug as the deadlock, but they share a root cause: AI agents produce code that *looks correct* at the function level without verifying that the system-level behavior matches the original. The deadlock is a concurrency manifestation. The str_app hardcoding is a data fidelity manifestation. Flamestrike is a logic registration manifestation. Different surfaces, same blind spot.

## What the Goroutine Dump Taught Us

The deadlock diagnosis required `SIGQUIT` — sending a signal to the running process to dump all goroutine states. Without it, we'd still be guessing. The dump showed goroutine 43 stuck on `writerSem` (Go RWMutex writer starvation), with no goroutine holding an active read lock.

This is underutilized as a diagnostic tool. Most MUD server operators look at logs. Logs are useless when the logger is deadlocked. Goroutine dumps are the only reliable way to diagnose concurrency failures in production Go services.

For the paper: a standing order to capture goroutine dumps on server hangs — or better, a health check that detects goroutine accumulation and dumps automatically — would catch an entire class of bugs that static analysis cannot see.

## The Numbers That Matter

Coverage before the fix: `pkg/session` at 6.2%, `char_creation.go` at 0%.

Coverage after: `pkg/session` at 12.7%, with 93 new tests covering the critical paths. The concurrent character creation regression test runs 5 goroutines through the full creation flow in 0.09 seconds.

The percentage sounds low. It's not. The package is 13,412 lines. The critical paths — login, character creation, command dispatch, door commands — now have dedicated tests. The number is low because the package is large, not because the tests are weak.

This is the lesson: coverage percentages are misleading for large packages. What matters is whether the *critical integration paths* are tested. A package at 5% coverage with tests on every player-facing path is safer than a package at 40% coverage that tests getters and setters.

## Implications for AI-Assisted Software Engineering

The deadlock story is a data point for a broader claim: **AI-generated codebases have systematic testing blind spots on integration and concurrency paths.**

The blind spots aren't random. They follow a pattern:

1. **Unit-level correctness is high.** AI agents write functions that compile and pass individual tests. The str_app function returns a number. The flamestrike function does damage. The Manager.Register function adds a player.

2. **Integration paths are untested.** The sequence login → char creation → session takeover → world registration crosses four packages and three mutex boundaries. No unit test covers this. AI agents don't write integration tests for paths they don't exercise.

3. **Concurrency is invisible.** Deadlocks and data races require *running* the code under load. Static analysis can't see them. AI agents that generate code sequentially don't think about concurrent access patterns unless explicitly prompted.

4. **Agent testing bypasses human paths.** When the testing agent (BRENDA) auto-creates players via the API, it skips the character creation wizard entirely. The path that real players take — the path with the deadlock — is never exercised by automated testing because the automated tester has a shortcut.

The fix isn't "write better prompts." It's architectural: AI-generated codebases need *integration test generation* as a first-class step in the porting pipeline, not an afterthought. The tests need to exercise the paths that real users take, under the concurrency conditions that real servers produce.

Until then, the goroutine dump is your friend.
