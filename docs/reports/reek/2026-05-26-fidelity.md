# Fidelity Audit — Week 3: Core Commands, Stealth & Economy
**Date:** 2026-05-26
**Focus:** Port fidelity of core gameplay, stealth skills, item consumption, special procedures, and housing subsystems in `pkg/game/` vs C source in `src/`
**Suffix:** fidelity-week3

## Summary

This audit systematically compares Go ports in `pkg/game/` and `pkg/session/` against their corresponding C lineage in `src/act.other.c`, `src/act.item.c`, `src/house.c`, `src/boards.c`, `src/mail.c`, and `src/spec_procs*.c` following the methodology outlined in **DP-192** (`docs/briefs/port-fidelity-audit-brief.md`). 

We expanded our initial audit (Option B) by executing automated static tests and checking the command dispatcher and special procedure bindings. This expanded pass successfully identified **13 major findings** (2 CRITICAL, 5 HIGH, 5 MEDIUM, 1 UNREGISTERED_SPECS) representing significant gameplay gaps in the Go engine.

## CRITICAL

### CRIT-001: doUse command is a complete stub for item-type routing

- **Go file:** [other_economy.go](file:///Users/zach/.openclaw/workspace/darkpawns_repo/pkg/game/other_economy.go#L172-L177)
- **C source:** `src/act.other.c:do_use()`
- **Severity:** CRITICAL
- **Type:** STUB
- **Description:** In C, `do_use` parses the chosen item, matches its type (e.g., ITEM_STAFF, ITEM_WAND, ITEM_POTION, ITEM_SCROLL, ITEM_PORTAL), and triggers the appropriate magical/physical effects via `mag_objectmagic`. In Go, the routing is completely absent. The code simply prints a generic text message `"You use [itemArg]."` and returns `true` without executing any effects.
- **Impact:** All consumable magic items (wands, staves, potions, scrolls) and interactive objects are completely non-functional when players try to `use` them.
- **Recommendation:** Implement proper item-type routing in `doUse` and wire it up to `pkg/spells` (e.g. `CallMagic`).

### CRIT-002: Object and Room Special Procedures are ignored by the Command Dispatcher

- **Go file:** [boards.go](file:///Users/zach/.openclaw/workspace/darkpawns_repo/pkg/game/boards.go#L7-L8)
- **C source:** `src/comm.c` / `src/interpreter.c`
- **Severity:** CRITICAL
- **Type:** MISSING_EDGE_CASE
- **Description:** While object special procedures (e.g., `genBoard` for bulletin boards) and room special procedures (e.g., `pray_for_items`, `jail`, `dump`) are registered and assigned, the main MUD command dispatcher in the session layer never checks or invokes `GetObjSpec` or `GetRoomSpec` before executing commands.
- **Impact:** **All bulletin boards and room specials are completely broken.** Typing `read`, `write`, `remove`, or `look` at a board is treated as a standard player command rather than triggering board operations, making communication systems inert.
- **Recommendation:** Update the session layer's command processing pipeline to check and run special procedures on rooms and nearby objects before routing to standard command handlers.

## HIGH

### HIGH-001: DoSteal is not implemented for Mob targets

- **Go file:** [skill_stealth.go](file:///Users/zach/.openclaw/workspace/darkpawns_repo/pkg/game/skill_stealth.go#L132-L177)
- **C source:** `src/act.other.c:do_steal()`
- **Severity:** HIGH
- **Type:** SIMPLIFICATION
- **Description:** In Go, stealing items is explicitly restricted to player targets via a type assertion (`if p, ok := target.(*Player)`). If the target is a mob, it falls through to a default `"You can't steal that."` message. Furthermore, gold stealing from mobs yields a hardcoded random amount without modifying mob assets, and the weight penalty (`GET_OBJ_WEIGHT`) calculation is commented out.
- **Impact:** Thieves are completely unable to steal items from monsters, removing a core combat-skipping and gear-acquisition loop.
- **Recommendation:** Extend `DoSteal` to support `*MobInstance` targets, check mob inventory lists, and uncomment object weight calculations.

### HIGH-002: DoMindlink type assertion always fails on Mobs

- **Go file:** [skills2.go](file:///Users/zach/.openclaw/workspace/darkpawns_repo/pkg/game/skills2.go#L248-L250)
- **C source:** `src/new_cmds2.c:do_mindlink()`
- **Severity:** HIGH
- **Type:** MISSING_EDGE_CASE
- **Description:** In `DoMindlink`, the success path attempts to transfer mana to the target using a type assertion to `*Player` (`p, ok := target.(*Player)`). However, the command checks earlier that the target is an NPC. In this codebase, NPCs are represented by `*MobInstance` rather than `*Player`. Thus, the type assertion always fails, and mobs never receive any mana.
- **Impact:** The `mindlink` skill is mechanically broken: it successfully drains the player's health but fails to transfer any mana to their charmed mob follower.
- **Recommendation:** Modify `DoMindlink` to check and set mana on `*MobInstance` targets (or support a unified interface on `combat.Combatant`).

### HIGH-003: DoDig loot table is purely textual and yields no items

- **Go file:** [skills2.go](file:///Users/zach/.openclaw/workspace/darkpawns_repo/pkg/game/skills2.go#L436-L446)
- **C source:** `src/new_cmds2.c:do_dig()`
- **Severity:** HIGH
- **Type:** STUB
- **Description:** `DoDig` rolls against the player's dig skill and prints a success message stating the player found coins, a rock, an old bone, or a gem. However, it only prints the text message; it never instantiates the objects or adds coins to the player's character sheet/inventory.
- **Impact:** Digging is a cosmetic placeholder. Players expend move points and health digging but receive absolutely no physical in-game items.
- **Recommendation:** Integrate with `world.objs` prototypes to instantiate real objects and place them in the player's inventory or the room floor.

### HIGH-004: canSee ignores invisibility, hiding, and blindness

- **Go file:** [act.go](file:///Users/zach/.openclaw/workspace/darkpawns_repo/pkg/game/act.go#L120-L127)
- **C source:** `src/utils.h:CAN_SEE()`
- **Severity:** HIGH
- **Type:** SIMPLIFICATION
- **Description:** In Go, the `canSee` function (used for character-to-character visibility checks) only verifies if the observer is awake (`observer.GetPosition() > PosSleeping`). Unlike the C version, it ignores critical checks for the `AFF_INVISIBLE`, `AFF_HIDE`, and `AFF_BLIND` affects, as well as room light levels and character level brackets.
- **Impact:** Awake characters can see invisible or hiding mobs and players perfectly, even if they are blind. This breaks basic stealth, illusion spells, and blindness mechanics.
- **Recommendation:** Replace the simplified awake-only check in `canSee` with a robust visibility check (similar to `canSeeObject`).

### HIGH-005: Item "use" command hijacked by Skill "use" command

- **Go file:** [commands.go](file:///Users/zach/.openclaw/workspace/darkpawns_repo/pkg/session/commands.go#L121)
- **C source:** `src/interpreter.c`
- **Severity:** HIGH
- **Type:** MISSING_EDGE_CASE
- **Description:** In CircleMUD/DikuMUD, players type `use <wand/staff>` to use magic items, and simply type the skill name (e.g. `backstab`) to use active skills. In the Go port, the `"use"` command string is registered exclusively to `CmdUseSkill` (e.g., `use backstab`), and has no delegation or command-routing path to run `doUse` on wands or staves.
- **Impact:** Players are completely unable to use staves or wands because the command is completely intercepted for skill usage.
- **Recommendation:** Reroute the `"use"` command handler in `pkg/command/` to check if the target argument is a wand/staff in inventory first, and fall back to skill usage if not.

## MEDIUM

### MED-001: doDrink and doEat ignore hunger, thirst, and drunkenness stats

- **Go file:** [item_consumable.go](file:///Users/zach/.openclaw/workspace/darkpawns_repo/pkg/game/item_consumable.go#L93-L97)
- **C source:** `src/act.item.c:do_drink()` / `do_eat()`
- **Severity:** MEDIUM
- **Type:** SIMPLIFICATION
- **Description:** In `doDrink` and `doEat`, the effects of food and drink on the player's hunger, thirst, and drunkenness stats are completely discarded (`_ = drunkAff`, `_ = fullAff`, `_ = thirstAff`).
- **Impact:** Hunger, thirst, and intoxication systems do not function. Players can consume items infinitely without hitting fullness limits, and starve/dehydrate checks do not apply.
- **Recommendation:** Wire these values directly to the player's condition attributes (e.g. `p.Conditions`).

### MED-002: spec_procs4 portals skip room description displays

- **Go file:** [spec_procs4.go](file:///Users/zach/.openclaw/workspace/darkpawns_repo/pkg/game/spec_procs4.go#L246) and [spec_procs4.go](file:///Users/zach/.openclaw/workspace/darkpawns_repo/pkg/game/spec_procs4.go#L290)
- **C source:** `src/spec_procs.c`
- **Severity:** MEDIUM
- **Type:** STUB
- **Description:** In `specEnterCircle` and `specElevator`, after the player is teleported to `portalRoom` or `elevatorDest`, the Go port contains a `// do_look placeholder` comment but does not execute the look action.
- **Impact:** Players traveling through these portals are moved to a new room but receive no text describing the room, leaving them disoriented.
- **Recommendation:** Execute a look command handler (e.g. `doLook`) after the player is successfully moved.

### MED-003: House player name/ID lookups are default nil stubs

- **Go file:** [houses.go](file:///Users/zach/.openclaw/workspace/darkpawns_repo/pkg/game/houses.go#L56-L79)
- **C source:** `src/house.c:get_name_by_id()`
- **Severity:** MEDIUM
- **Type:** STUB
- **Description:** `getPlayerNameByID` and `getPlayerIDByName` are declared as package-level function pointers that default to `nil`. Although guards prevent panics, `RegisterHousePlayerLookup` is never called during server initialization.
- **Impact:** House guest lists and owners cannot resolve player names, resulting in blank names or failures when managing guests by name.
- **Recommendation:** Call `RegisterHousePlayerLookup` in server startup (e.g., in `cmd/server/main.go` or `pkg/session/`) and back it with SQLite database queries.

### MED-004: cmdWrite is a cosmetic placeholder for writing notes

- **Go file:** [comm_cmds.go](file:///Users/zach/.openclaw/workspace/darkpawns_repo/pkg/session/comm_cmds.go#L337-L364)
- **C source:** `src/act.comm.c:do_write()`
- **Severity:** MEDIUM
- **Type:** STUB
- **Description:** The `write` command does not check if the target item is a writable note (`ITEM_NOTE` type 23), doesn't require a pen in inventory, and doesn't actually store the written message on the item.
- **Impact:** Note writing is purely cosmetic. Players see a success message, but the text is never saved to the note, leaving it blank.
- **Recommendation:** Add type checks, inventory checks, and update the item description/state with the written message.

### MED-005: Postmaster NPC special procedure is unregistered and inert

- **Go file:** [spec_assign.go](file:///Users/zach/.openclaw/workspace/darkpawns_repo/pkg/game/spec_assign.go#L47,L314)
- **C source:** `src/mail.c`
- **Severity:** MEDIUM
- **Type:** STUB
- **Description:** The special procedure `"postmaster"` is assigned to NPC vnums 3010 and 21225 in `spec_assign.go`, but `RegisterSpec("postmaster", ...)` is never called anywhere. The MUD mail system (`mail.go`) is fully ported but entirely un-wired.
- **Impact:** **The MUD mail system is completely broken.** Postmaster NPCs are inert and players cannot send, check, or receive mail.
- **Recommendation:** Wire up a Postmaster spec function in `pkg/game/` that delegates to `PostmasterSendMail`, `PostmasterReceiveMail`, and `PostmasterCheckMail`, and register it in `SpecRegistry`.

## UNREGISTERED SPEC PROCEDURES

We created an automated unit test (**[spec_assign_validation_test.go](file:///Users/zach/.openclaw/workspace/darkpawns_repo/pkg/game/spec_assign_validation_test.go)**) to check for assigned but unregistered spec procs. In addition to `"postmaster"` (documented above), the test identified **5 other major legacy special procedures** that are mapped to mobs/objects in `spec_assign.go` but are completely missing from the `SpecRegistry`:

1. **`"moon_gate"` (VNums 4001, 4002, 19604-19611):** Object special procedure defined in C `gate.c` that spawns shimmering portals reacting to moon phases during the night, allowing travel between sectors. **Currently completely inert; portals do not function.**
2. **`"no_get"` (VNums 14416, 14430):** Mob special procedure in C `new_cmds2.c` that strikes at player hands and initiates combat when trying to get/take items in the room. **Currently silent; mobs let players loot everything.**
3. **`"recharger"` (VNum 8):** NPC special procedure in C `new_cmds2.c` that recharges player wands and staves for gold while reducing the item's maximum charge cap. **Currently inert; no recharge services.**
4. **`"beholder"` (VNum 11011):** Mob special procedure in C `new_cmds2.c` that blocks spell-casting in the room, casts random charm/sleep/curse affects on idle players, and fires disintegrate spells in combat. **Currently a generic mob with no special beholder logic.**
5. **`"zen_master"` (VNum 18219):** Mob special procedure in C `new_cmds2.c` that teleports or recalls attacking characters away to stop violence. **Currently a generic mob.**
