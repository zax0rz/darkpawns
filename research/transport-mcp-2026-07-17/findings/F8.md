# F8: MUD-Specific MCP Considerations

## Findings

### [1] GMCP uses telnet option 201 as an out-of-band channel, making it a direct historical precedent for what MCP would do differently — JSON-RPC over HTTP instead of telnet subnegotiations.
- quote: "The intention of GMCP (and its predecessors such as ATCP) is to allow 'out of band' information to be sent from the MUD server to the client, or the client to the server. In this context 'out of band' means 'invisible to the player'."
- url: https://www.gammon.com.au/gmcp
- source_type: primary (Nick Gammon, author of MUSHclient, adapted from mudstandards.org)
- published: 2015-04-08 (amended 2020-04-28)
- confidence: high

### [2] MSDP (option 69) has a REPORT mechanism where the server pushes variable changes automatically — this is the MUD world's solution to the push-not-polling problem that MCP must also solve for combat events.
- quote: "When receiving a REPORT request the server should send the requested variables to the client, and re-send each individual variable whenever it changes."
- url: https://tintin.sourceforge.net/protocols/msdp/
- source_type: primary (Scandum, MSDP protocol author)
- published: unknown
- confidence: high

### [3] MCP's Streamable HTTP transport supports server-initiated SSE streams, which is the protocol's native mechanism for push notifications — a client can open a GET SSE stream and the server sends JSON-RPC requests/notifications on it asynchronously.
- quote: "The client MAY issue an HTTP GET to the MCP endpoint. This can be used to open an SSE stream, allowing the server to communicate to the client, without the client first sending data via HTTP POST."
- url: https://modelcontextprotocol.io/specification/2025-03-26/basic/transports
- source_type: primary (MCP spec 2025-03-26)
- published: 2025-03-26
- confidence: high

### [4] MCP tools are request-response (client sends tools/call, server returns result) with no built-in event stream per invocation — this means combat round events cannot be pushed as tool results and must use the SSE notification channel or resource subscriptions instead.
- quote: "To invoke a tool, clients send a tools/call request... Response: { 'jsonrpc': '2.0', 'id': 2, 'result': { 'content': [...] } }"
- url: https://modelcontextprotocol.io/specification/2025-03-26/server/tools
- source_type: primary (MCP spec 2025-03-26)
- published: 2025-03-26
- confidence: high

### [5] MCP resource subscriptions provide a server-to-client push mechanism: a client subscribes to a resource URI, and the server sends notifications/resources/updated when it changes — this maps directly to subscribing to combat state or room state changes.
- quote: "Clients can subscribe to specific resources and receive notifications when they change: Subscribe Request: { 'method': 'resources/subscribe', 'params': { 'uri': 'file:///project/src/main.rs' } }"
- url: https://modelcontextprotocol.io/specification/2025-03-26/server/resources
- source_type: primary (MCP spec 2025-03-26)
- published: 2025-03-26
- confidence: high

### [6] GMCP uses JSON as its data format, the same encoding as MCP — this means structured game state (room info, character vitals, combat data) already has a JSON representation in the MUD ecosystem, which can be adapted rather than invented from scratch.
- quote: "The <data> part... is typically implemented on the Client-side using a JavaScript Object Notation (JSON) parser."
- url: https://www.gammon.com.au/gmcp
- source_type: primary
- published: 2015-04-08
- confidence: high

### [7] MSDP defines standard combat variables (OPPONENT_NAME, OPPONENT_HEALTH, OPPONENT_LEVEL) and character vitals (HEALTH, MANA, MOVEMENT) — these are the exact data payloads an MCP combat subscription would need to expose, and the naming convention is battle-tested across MUDs.
- quote: "OPPONENT_NAME: Name of opponent. OPPONENT_HEALTH: Current health points of opponent. HEALTH: Current health points. MANA: Current mana points."
- url: https://tintin.sourceforge.net/protocols/msdp/
- source_type: primary
- published: unknown
- confidence: high

### [8] MCP stdio transport uses newline-delimited JSON-RPC over stdin/stdout, making it unsuitable for integration with a telnet-based MUD server that already multiplexes binary telnet negotiation sequences — Streamable HTTP is the only viable MCP transport for Dark Pawns.
- quote: "Messages may be JSON-RPC requests, notifications, responses—or a JSON-RPC batch containing one or more requests and/or notifications. Messages are delimited by newlines, and MUST NOT contain embedded newlines."
- url: https://modelcontextprotocol.io/specification/2025-03-26/basic/transports
- source_type: primary
- published: 2025-03-26
- confidence: high

### [9] GMCP and MSDP both use telnet subnegotiation (IAC SB ... IAC SE) as transport, meaning they interleave with the player's text stream — MCP's HTTP-based transport is architecturally separate from the telnet connection, which is exactly the isolation needed for agent-only access.
- quote: "IAC SB GMCP Package[.SubPackages].Message <data> IAC SE — That is: 0xFF 0xFA 0xC9 package.message <data> 0xFF 0xF0"
- url: https://www.gammon.com.au/gmcp
- source_type: primary
- published: 2015-04-08
- confidence: high

### [10] MCP logging notifications (notifications/message) provide a server-initiated push channel with severity levels — this could serve as a lightweight event bus for non-critical game events (area repops, channel messages) without requiring full resource subscription overhead.
- quote: "Servers send log messages using notifications/message notifications... { 'method': 'notifications/message', 'params': { 'level': 'info', 'logger': 'database', 'data': {...} } }"
- url: https://modelcontextprotocol.io/specification/2025-03-26/server/utilities/logging
- source_type: primary (MCP spec 2025-03-26)
- published: 2025-03-26
- confidence: medium

### [11] The GMCP predecessor ATCP (option 200) was originally built for Iron Realms Entertainment's Achaea — the lineage from ATCP→GMCP→MCP shows the MUD community has been iterating on out-of-band structured data for 20+ years, and MCP is the latest evolution using web-native transports.
- quote: "Previously GMCP was known as ATCP2 where ATCP is the Achaea Telnet Client Protocol... The protocol number for ATCP was 200 (not 201)."
- url: https://www.gammon.com.au/gmcp
- source_type: primary
- published: 2015-04-08
- confidence: high

## Dead ends
- MXP (MUD Extension Protocol) docs at zuggsoft.com and tintin.mudhalla.net returned 404 — MXP is less relevant since it's markup-in-band (HTML-like tags in text) rather than out-of-band structured data like GMCP/MSDP.
- mud.gamepedia.com GMCP page returned 404 — wiki may have been taken down.
- Web search API was unavailable; all findings derived from direct URL fetches of known primary sources.
- No existing MCP MUD server implementations were found to reference — this appears to be a novel integration.

## Suggested follow-ups
- Investigate how MCP's resource subscription mechanism handles high-frequency updates (combat rounds every 1-2 seconds) — does the SSE stream keep up, or is batching/throttling needed?
- Research whether any Go MCP SDK exists (or if JSON-RPC over HTTP must be hand-rolled) — the transport layer is the critical implementation detail for Dark Pawns.
- Determine if MCP's session management (Mcp-Session-Id) can map 1:1 to a MUD player session, or if a multiplexing layer is needed for multiple concurrent agents per player.
